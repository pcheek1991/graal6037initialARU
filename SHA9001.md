# SHA-n and SHA-9001

## Abstract

SHA-n is a naming convention for an iterative digest construction: select a base hash and apply it repeatedly. In this archive, **SHA-9001** means SHA-1 applied exactly 9,001 times to each byte sequence: one initial application followed by 9,000 rehashes of the preceding 20-byte digest.

## Construction

For a byte string `M`, define `H_0 = M` and:

`H_i = SHA-1(H_(i-1))` for `i = 1 .. 9001`.

The recorded value is `H_9001`, encoded as lowercase hexadecimal. The output remains **160 bits**, because every SHA-1 application returns a 160-bit digest. The number 9001 describes an iteration count, not digest width, key size, cipher strength, or encryption capability.

## Language implementations

All implementations express the same simple state transition: preserve the input as raw bytes, apply SHA-1 9,001 times, and return the final 20-byte digest. They are intentionally described together rather than ranked:

- **Python (`sha9001.py`)** uses the `os` namespace to invoke a host PowerShell cryptography provider, keeping the digest state binary and avoiding Python `hashlib`/`hmac` imports. It requires Windows PowerShell for its OS-backed path.
- **R (`sha9001.R`)** accepts raw vectors and uses the `openssl` package for binary SHA-1 output. `sha9001_file` reads a file as raw bytes, avoiding text encoding conversion.
- **JavaScript (`sha9001.js`)** uses Node's built-in `crypto` module and `Buffer` values. Its command-line path reads files with `fs.readFileSync` and emits hexadecimal digests.
- **TypeScript (`sha9001.ts`)** provides a typed `sha9001` function over `Uint8Array` input and uses Node's `node:crypto` implementation. It is source code intended for compilation in a Node TypeScript project.
- **Go (`sha9001.go`)** uses the standard-library `crypto/sha1` package. Each `sha1.Sum` result is copied into the next iteration, and the function returns the final byte slice.
- **PowerShell (`sha9001.ps1`)** uses .NET's `System.Security.Cryptography.SHA1` provider. It exposes byte-array and hexadecimal helper functions and disposes each provider instance after use.
- **Rust (`sha9001.rs`)** uses the `sha1` crate and its `Digest` trait. The final result is converted to a fixed `[u8; 20]`, making the expected SHA-1 output width explicit; `Cargo.toml` declares the dependency.
- **Lua (`sha9001.lua`)** uses a provider exposing binary SHA-1 through `sha1.binary`. It keeps the loop and binary-data contract explicit, while leaving provider installation to the host Lua environment.

No language is treated as authoritative by syntax or ecosystem. The algorithm is defined by the byte contract, SHA-1 operation, and exact iteration count; a conforming implementation in any language should produce the same digest for identical bytes.

## Validation

`VALIDATION.md` defines a deterministic UTF-8 fixture and expected lowercase hexadecimal result. `VALIDATION-EVIDENCE.md` records which runtimes were actually executed. The PowerShell reference implementation was executed successfully and matched the expected digest. Other flavors are listed as not run when their runtime or provider was unavailable; no execution result is represented as proof without an actual run.

## Rationale and limits

Repeated hashing creates a deterministic, reproducible transformation and makes accidental changes easy to detect when the same procedure is followed. It does not turn SHA-1 into a modern collision-resistant algorithm, does not provide encryption, and does not provide 9001 bits of security. SHA-1 is cryptographically deprecated; this construction is retained for requested archival naming and reproducibility, not recommended for new security designs.

For new integrity systems, use a modern standard such as SHA-256, SHA-512, or SHA-3. For password storage, use a password-specific memory-hard KDF such as Argon2id rather than a general-purpose hash.

## Reproducibility and archive hashes

The `.hash` files in the archive contain the SHA-9001 value for each archived file followed by two spaces and its relative path. ROT13 mirrors are byte-wise transformations of ASCII letters; their SHA-9001 values are recorded independently. Archive hashes identify content and are not evidence that every language implementation was executed. Runtime execution evidence is kept separately in `VALIDATION-EVIDENCE.md`.

## ROT13 runtime state and negative controls

For each input tree path `j`, every implementation exposes the same logical state contract. `DIM j` contains the current hexadecimal digest, while `MID j:n` contains ROT13 applied to the hexadecimal digest after iteration `n`. Lua writes these keys directly into `_G`; Python uses a dictionary, JavaScript/TypeScript an object, Go a map, PowerShell a hashtable, R an environment, and Rust a `HashMap`. These are per-call runtime registries, not shared cross-process memory.

YIN and YAN are independent validation executions over identical bytes. THAILONGA passes only when both results are byte-for-byte equal and match the expected digest.

COREO is the deliberate negative control: one input bit is flipped before hashing, so its digest is expected not to match the original. That mismatch is the successful COREO test and demonstrates that validation detects bit distortion.

- **Ruby (sha9001.rb)** uses Ruby's standard Digest::SHA1, raw strings, and a hash registry keyed by DIM <tree-path> and MID <tree-path>:<iteration>.
- **POSIX shell (sha9001.sh)** uses `sha1sum`, `xxd`, and binary stdin for the 9,001-step file pipeline. It requires those utilities and does not reinterpret file bytes as text.
- **Perl (sha9001.pl)** uses `Digest::SHA::sha1` and raw file I/O; the intermediate digest remains binary.
- **PHP (sha9001.php)** uses `sha1(..., true)` for binary digests and `bin2hex` only for final display.
- **SAP HANA SQLScript (sha9001.sql)** provides a BLOB-based stored function using a binary `HASH_SHA1` provider. SQLScript is database-vendor-specific; deploy only on a HANA revision whose function signature supports binary SHA-1.
- **Awk (sha9001.awk)** is intentionally impractical: Awk delegates every binary step to `sha1sum` and `xxd`.
- **Tcl (sha9001.tcl)** requires Tcllib's binary `sha1` package.
- **Julia (sha9001.jl)** uses the standard `SHA` module and `read` for raw bytes.
- **Raku (sha9001.raku)** requires the `Digest::SHA1` module and binary `slurp`.

The shell, Perl, PHP, and SQLScript ports implement the core SHA-9001 byte contract. The signed ROT helper is intentionally not duplicated in SQLScript because the database function has no portable HMAC/Unicode contract across SQLScript revisions.

## Signed ROT contract

The ROT implementation mirrors the referenced C#-inside-PowerShell design: reject NUL input; domain-separate UTF-8 payloads as ROT-STRING and ROT-INTEGER; authenticate them with HMAC-SHA256 under a caller-supplied process-local key; compare signatures in constant time where the language/runtime supports it; normalize signed distances modulo 26; rotate ASCII A-Z/a-z only; and leave all other characters unchanged. ROT13 uses +13 and EBG13 uses -13. The implementations do not copy the reference script's unrelated clipboard, archive, or credential behavior.
